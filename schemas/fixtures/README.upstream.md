# Conformance fixtures

Positive and negative vectors for every drafted schema. They are the mechanism by which a
consuming workstream can implement against a contract without importing another unfinished
worktree, which is gate G1.

## Running them

```sh
npm i --prefix /tmp/ws00-validate ajv@8 ajv-formats@3
NODE_PATH=/tmp/ws00-validate/node_modules node schemas/validate.mjs
NODE_PATH=/tmp/ws00-validate/node_modules node schemas/validate.mjs --explain
```

`--explain` prints, for each negative fixture, the reason it is expected to be rejected next to
the schema keywords that actually rejected it. Use it when changing a schema: a negative fixture
that starts failing for a different reason is no longer testing what it claims to test.

`ajv` is deliberately not vendored here. This repository holds contracts, not code, and adding a
lockfile and `node_modules` to it would make the contract set look like a package.

## Conventions

- `valid/<schema-basename>.<case>.json` must validate.
- `invalid/<schema-basename>.<case>.json` must be **rejected**, and carries a top-level
  `$expectedError` string naming the invariant under test. The runner strips that key before
  validating. An invalid fixture that passes is reported as a failure, because a negative vector
  that does not actually fail is a silent hole in the contract.

## Addresses in fixtures are synthetic

Every address here is an obvious placeholder such as `0x…00a1`. None is a real deployment
address. Real values belong in a deployment manifest generated by WS01 from pinned artifacts.
`AGENTS.md` forbids hand-copying addresses, and a fixture is exactly the kind of file from which
a wrong address would be copied into production code later.

## Coverage

Positive: direct and x402 crossed with identity `none` and `erc8004`; an enabled testnet manifest
and a disabled mainnet manifest; verified, partial and orphaned-identity verification results;
transaction and settlement receipts including an unread receipt and an unknown settlement; a
completed direct job, a partial-success job, a job interrupted while its commitment matures, and
a job holding an unknown settlement.

Negative: the mode/custody combinations the intent forbids, identity-hash mismatches, a bare
network nickname instead of CAIP-2, a numeric big integer, a permissive canonicality flag, an
inlined ABI, an unknown error code, a secret in a free-form details object, a settlement receipt
carrying a reusable payment authorization, a job storing a raw commitment secret, a job claiming
two settlements, a completed job with no result, a provider job with no idempotency key, and a
provider field leaking into the common result.

The last one is worth stating plainly: the requirement that provider-specific fields never leak
into the common final result is enforced structurally, so an integration test cannot tell direct
from x402 execution by inspecting the shape of `result`.

## 0.2.0 additions (G1 sign-off round)

Positive: a resource-anchored identity that survives a role change; a completed provider-custody
transfer; approved and MFA-pending signature receipts; a terminal orphaned-binding error.

Negative, one per invariant added in this round: identity binding marked retryable without a
confirmed revert; an indeterminate error routed to `retry_same_step`; an orphaned binding marked
retryable; a verified result resting on a drifted registry, a single RPC endpoint, or disagreeing
endpoints; a verified custodial job whose transfer never completed; `bound: true` with no binding
standard, discovery match, or anchor; a `deploy-owned` resolver with no predicted address; an
ERC-8004 intent with no pinned adapter implementation; a direct job carrying a provider block or a
custodial mode; an unknown settlement that schedules another payment; and a resume that re-enters
directly at `identity_bind` instead of `identity_preflight`.

Each was confirmed with `--explain` to fail on the specific keyword that encodes its invariant.

## Confirmation-round patch (2026-08-25, schemas at 0.3.0)

Positive: a custodial job verified with a completed transfer and a full resource anchor; a
provider-origin job holding a durable identity anchor before binding.

Negative, one per objection raised by the five consuming workstreams: a verified result with the
custody block deleted; a custody mode contradicting `transferRequired` in both directions; a bound
anchor that survives re-registration; a resource anchor claimed without the epoch re-read; a job
that reached `identity_bind` with no durable anchor; the three ways the never-blind-repay guard
could be bypassed (omit `outcome`, mislabel it `pending`, drop `resume`); a misspelled
`resumeFromStep`; and a settlement receipt with a non-hash idempotency key or no `intentHash`.

The two settlement negatives report `oneOf` noise in aggregate output because the transaction
branch also fails. Validated against the settlement branch alone, they reject on exactly
`required: intentHash` and the `hash32` pattern respectively.

## Fixture versions are mixed, on purpose

`verification-result`, `step-receipt` and `provisioning-job` are at 0.3.0; the other four schemas
are still at 0.2.0. Fixtures carry the `schemaVersion` of the schema they exercise, so a
`provisioning-intent` fixture reads `0.2.0` and a `provisioning-job` fixture reads `0.3.0` in the
same directory. A job fixture embeds a verification result, so its nested `result.verification`
also carries `0.3.0`. This is per-schema versioning working as intended, not drift.

## Preflight-gap patch (2026-08-25)

Positive: a job in the ENS-complete/identity-pending state with **no** `identity_bind` step yet,
carrying a recorded `identityAnchor`. This is adapter8004's probe case, which previously validated
without an anchor.

Negative: the same job with the anchor removed, which isolates the new trigger — it carries no
`identity_bind` step, so only the registration-onward rule can reject it. Plus an intent pairing
`anchorKind: resource` with `bindingStandard: erc721`, which is signable but unperformable.
