### What this run specifically proves

**The mainnet adapter is real, and it is not at Sepolia's address.** Through 0.9.0 this plugin pinned no `adapter8004` for chain 1 and refused every `agent *` command there, because it tested Sepolia's `0x7621630c…` against mainnet and read back no code. Agent #56108 was minted through `0xde152AfB7db5373F34876E1499fbD893A82dD336`, the adapter that was live the whole time — since block 26285388, which is 48 blocks *before* the block the mainnet table was originally derived at.

**Each chain has its own ERC-8004 registry.** The ENSIP-25 key written here is `agent-registration[0x000100000101148004a169fb4a3325136eb29fa0ceb6d2e539a432][56108]` — ERC-7930 for chain `0x01` plus registry `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432`, read from the adapter's own `identityRegistry()`. 0.9.0 would have written Sepolia's `0x8004A818BF…` here, pointing every reader at a registry this agent does not appear in. The record is resolved and rendered independently by the ENS manager app, which displays registry `8004.eth` and agent id `56108` on the name.

**A paid step is not re-sent when it is already done.** The Sepolia rehearsal of this same ladder ran out of gas between the USDC approval and the register call. Rerunning the identical command resumed from the private checkpoint with `resumedCommitment: true` and `approve: null` — it reused the commitment, skipped the approval it had already paid for, and sent only the register transaction.

## What the run proved

- Detection confirms the selected deployment is really serving its generation of ENSv2, on every command, and refuses any chain with no pinned table.
- A resolver's address is predicted correctly before deployment and attested after.
- Registration lands with the resolver bound, and a real interruption resumed without a duplicate payment.
- An agent is minted and bound in one transaction, and the name's ENSIP-25 link makes it findable.
- Both directions of resolution hold for both wallets.
