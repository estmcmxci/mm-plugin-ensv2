# Deployment table

The plugin pins **4 deployments** across 2 chains — **Sepolia** (11155111) and **Ethereum mainnet** (1) — selected with `--deployment <sepolia|mainnet|hackathon|beta>` (or `MM_ENSV2_DEPLOYMENT`; default `sepolia`). Naming a deployment implies its chain and naming a chain implies that chain's canonical deployment, so neither flag needs the other; an incoherent pair is refused. Any chain without a pinned deployment is refused rather than guessed at.

The default is a **testnet** deliberately. Mainnet is pinned and fully supported, but spending real USDC is something you ask for with `--deployment mainnet`, never something you get by omission.

## Three generations, three gates

The tables span **three contract generations**, and the fail-closed gate never accepts one against another's contracts — each gate asserts the other generations' markers ABSENT, not merely its own present.

| Concern | g1 (`beta`) | g2 (`hackathon`) | g3 (`sepolia`, `mainnet`) |
|---|---|---|---|
| version probe | `supportsInterface(0xf99a5e06)` | `supportsInterface(0x1a6cc9f0)` | **`isENSv2()`; both ids `false`** |
| `isENSv2()` | reverts | returns `true` | returns `true` |
| registry navigation | on the Universal Resolver | on a separate `UniversalHelper` | same as g2 |
| resolver record setters | `setAddr`/`setText(bytes32 node, …)` | `setAddress`/`setText(bytes dnsName, …)` | same as g2 |
| resolver initializer | `initialize(address,uint256,bytes[])` | `initialize(Grant[],bytes[])` | same as g2 |
| forward + reverse resolution | `findResolver` / `resolve` / `reverse` on the UR | identical | identical |
| ERC-8004 binding | yes | yes | Sepolia only — no adapter on chain 1 |

**g3 is g2's contracts.** The deployed bytecode was compared selector by selector on 2026-10-27: `ETHRegistrar` is the same 8037 bytes with the same entry points on all three g2/g3 deployments, `PermissionedResolverImpl` exposes exactly the same setters and initializer, `VerifiableFactory` and `ETHRegistry` match to the byte. One set of encoders serves both; g3 is a separate generation only because its Universal Resolver stopped advertising the g2 ERC-165 id while still answering `isENSv2()`.

Addresses are never trusted blindly. `mm ensv2 status` re-derives the `.eth` registry from the deployment's own navigation surface and refuses to run if the table disagrees; the resolver factory's clone target, the adapter's implementation (EIP-1967 slot) and the reverse registrar (root → `reverse` TLD resolver → v1 registry → `owner(addr.reverse)`) are each re-derived on use.

## Names and agents are per deployment

A registration, a resolver, a primary name and an ERC-8004 binding all belong to the deployment they were made on. `mm ensv2 whois agent.eth` and `mm ensv2 whois agent.eth --deployment mainnet` are two different questions with two different answers, and a provisioning job created under one deployment refuses to resume under another (`E_UNSUPPORTED_DEPLOYMENT`).
