# ENSv2 in five minutes

ENSv2 is a rewrite of the ENS registry, live as a **beta on Sepolia**. The user-facing story is familiar: `name.eth` resolves to an address and carries records. Almost everything underneath is different.

## A hierarchy, not a flat map

ENSv1 kept every name in one registry keyed by `namehash`. ENSv2 is a tree of **registries**. The root registry holds top-level labels; the `.eth` registry holds second-level names; each name can have its own subregistry for its subnames. A name's owner, expiry, resolver and roles are read from the registry that *holds* it.

You never walk that tree by hand. The **Universal Resolver** (same address as mainnet, `0xeEeEEEeE14D718C2B47D9923Deab1335E144EeEe`) does it: `findResolver(name)` returns the resolver and how far up the tree it was found, `findParentRegistry(name)` returns the registry that holds the name, `findCanonicalRegistry("eth")` returns the `.eth` registry. Every read in this plugin goes through it, including verification after writes, so the plugin sees what any stranger sees.

## Your own resolver

There is no shared public resolver you write your records into. Each owner deploys a **resolver they control**, as a minimal proxy over an audited implementation, through a factory that can later prove what the proxy runs. Its address is predictable from your wallet before it exists, so a name can be registered with the resolver already bound. [Details](/explainer/resolver).

## Registration is commit, wait, pay in an ERC-20

Register a `.eth` name by committing to a hash, waiting at least 60 seconds and at most 24 hours, then revealing and paying, in the beta's test USDC rather than ETH. Minimum term is 28 days; the price curve is non-linear and quoted by the registrar itself (one year of `sesquipedalian.eth` was 8.000021 USDC). [Details](/explainer/registration).

## The token id moves

This is the one that bites. A name is a token in its registry, but the token id is **regenerated every time a role is granted or revoked** on the name, and again on re-registration. Anything that stores a token id as a durable pointer to a name silently detaches from it. The stable handles are the canonical id and the **registration epoch**; the plugin reports all three in `whois`, and the [identity](/explainer/identity#the-mutable-token-id) page explains the consequence for bound agents.

## Same address, different protocol

The Universal Resolver proxy shares its address with mainnet, and a v1-shaped client will happily call it. So the failure mode of ENSv1 code on ENSv2 is not an error. It is a plausible-looking wrong answer. The plugin therefore **refuses to run** unless five independent checks agree that the chain is serving ENSv2 and that its deployment table matches:

1. The Universal Resolver reports the v2 interface (`supportsInterface(0xf99a5e06)`).
2. `findCanonicalRegistry("eth")` equals the configured `.eth` registry.
3. The root registry's `getSubregistry("eth")` equals that registry.
4. That registry's `getParent()` is the root registry with label `eth`.
5. The resolver factory's `proxyLogic()` equals the configured clone target.

`mm ensv2 status` prints all five. `--chain 1` is refused outright: no mainnet deployment exists.

## One lesson from building it

The ENS contracts repository's `contracts/src/` tree describes a *different generation* of the resolver from what is deployed on Sepolia: a different initializer, different record setters, different role names. Code written against that source reverts on chain. The plugin was built against the checked-in deployment artifacts and the ENS documentation, which match the chain, and this site's [deployment table](/reference/deployment) records where every address came from.
